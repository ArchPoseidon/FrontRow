# Decisions

- App named FrontRow (brief title was ShowRadar); tagline "Be the first to know about a show."
- Project lives in `Mesa Ai/frontrow`, its own git repo, separate from the other projects in that folder.
- Next.js 16.4: `middleware.ts` is now `proxy.ts` (Node runtime). Proxy does only an optimistic session-cookie check; every page and API route re-checks the session server-side.
- Next 16 scaffold enables `cacheComponents`, so route segment config like `export const dynamic` is not allowed; route handlers are dynamic by default.
- Drizzle uses the `neon-http` driver via `@neondatabase/serverless`: one lightweight client per call, no pool to leak.
- `pg_trgm` is enabled at the top of the first migration (`drizzle/0000_init.sql`).
- Auth.js v5 with database sessions; only `openid email profile` scopes. Owner flag is set on sign-in when the email equals `OWNER_EMAIL`.
- Dark mode by default; light via `data-theme="light"`. All colours/radii live in CSS variables in `app/globals.css`.
- `/api/health` is public and reports only real values; per-job runs and Firecrawl credits are empty until those jobs exist.
- Secrets live in `.env.local` (gitignored) and in Vercel env vars; `.env.example` lists names only.
- shadcn/ui is deferred until the first component that needs it (Phase 1+), to keep Phase 0 minimal.
- Production URL: https://frontrow-pi-three.vercel.app (Vercel alias, stable). Deployed from CLI for now; GitHub link to be added so pushes to main deploy.
- Google consent screen stays in Testing mode by the owner's choice (deliberate change from the brief): judges' emails are added as test users in Google Cloud Console (max 100). Unlisted emails see Google's own "access blocked" page; /demo stays public. Switching to Publish later needs no code change.
- Phase 1: verified live APIs first. Gemini key works (sent as `x-goog-api-key`); newest stable Flash is `gemini-3.8-flash` (set as `GEMINI_MODEL`). Spotify search returns 10 results with photos and genres. MusicBrainz works with the User-Agent.
- Spotify search and artist lookup use the app's client-credentials token, not the owner's refresh token, so identity resolution keeps working even if the owner's personal connection breaks. The per-user connection (owner and allowlisted users) is used only for the followed/top import. Deviation from the brief's "owner token for search", for robustness.
- Spotify's redirect URI must use `127.0.0.1`, not `localhost`, so the Spotify connect flow is tested on the production URL (the Google sign-in cookie is on `localhost` locally).
- Resolution rules: auto-accept only when exactly one result matches the normalized name exactly; two exact matches (e.g. duplicate Spotify profiles for the same name) go to the "Which one?" tray. Nothing at all in Spotify or MusicBrainz becomes `unverified` ("Name only").
- `needs_review` is represented by open `artist_candidates` rows, not artist rows, so nothing unconfirmed is watched or matched.
- Alias enrichment (MusicBrainz aliases, origin, mbid) is best effort in `after()` with a 40s budget, because MusicBrainz answered at 2-3s per call. Artists beyond the budget keep derived aliases (leading "The", "&"/"and") and are enriched on a later pass.
- A MusicBrainz match by name alone is accepted only if it is a single perfect-score exact-name hit; otherwise the mbid comes from the Spotify URL relation or is left empty.
- First sign-in with `onboarding_step = 0` is redirected from `/radar` to `/onboarding`. Onboarding steps 1 and 2 are built; cities and alerts steps come in later phases.
- Phase 2: Gemini grounding and structured output are kept in separate calls (the combined call returned no text). Grounded sweep answers become raw items with `SOURCE_URL:` lines; grounding links are Google redirects, so each is followed once (4s budget) to the real page URL.
- Sweep "nothing announced" is decided by a structured field (`has_upcoming_india_show`), not by the word NONE, because the model wraps its answer in headings. Those sweeps store no raw item and spend no extraction call, but still update `last_checked_at` and "Last in India".
- News is pre-filtered before Gemini: a headline must name a watched artist (normalized, whole-word) to become a raw item. Generic feeds use the same gate. This keeps Gemini calls to real candidates only.
- Matching uses a JS port of pg_trgm similarity over the watched list (same measure, no per-name round trips); thresholds as in the brief (0.85, 0.92 for name-only, Gemini yes/no for 0.7-0.85).
- A sweep is about one named artist, so if Gemini spells that artist differently, the sweep's artist hint is trusted for non-festival events.
- Decide queues `alerts` rows (status `pending`, or `digest_pending` for info) but sends nothing: dispatch is Phase 3. Re-deciding is idempotent through the unique constraint; an unsent alert is upgraded if urgency rises.
- First-run scan: artists swept in the last 12 hours are not swept again (shared cache across users); up to 8 are swept, must-see first, and the rest are reported as "Deep check runs tonight".
- First-run finishes onboarding (`onboarded_at`, step 4) for now; the Cities and Alerts steps are inserted before it in Phase 3. `/welcome` is reached from "Find my shows" on the confirm step.
- Owner radar seeding (`scripts/seed-owner-radar.ts`): a grounded Gemini query finds artists with announced India shows, they are resolved through Spotify and set to must-see on the owner's list, then swept and processed. Everything stored carries real source URLs.
- Phase 3: Telegram bot is @FrontRowShowBot (username saved in env). Webhook registered with `scripts/set-webhook.ts`; every call checks `X-Telegram-Bot-Api-Secret-Token`, and the route always answers 200 so a bad update is never retried forever.
- Email templates are plain HTML strings, not React Email: one fewer dependency, same output. Unsubscribe links are HMAC-signed (AUTH_SECRET) and also work as one-click POST.
- Dispatch claims rows atomically (`for update skip locked`), so overlapping runs never double-send. At most 5 instant alerts per user and channel per run; the rest roll into the next digest (a first sync must not flood anyone).
- Telegram "blocked the bot" unlinks the chat and re-queues that alert by email. A failed poster image falls back to a text message with the same buttons.
- Alerts for events dated in the past are skipped, never sent. Email alerts stay `pending` (and are shown as waiting) until email credentials exist.
- The digest records one `digest` alert row per (user, event), so no event is in two digests; info alerts are included whatever their age.
- Test alert uses the nearest real event (home city first), labelled Test. Only with none, a stored `is_sample` event is used, labelled Sample.
- Onboarding steps 3 (cities) and 4 (alerts) are built; "Find my shows" on step 4 goes to /welcome. Existing onboarded users reopening /onboarding land on step 2.
- Phase 4: one `EventCard` component (compact and full; the poster size is the OG route). Card states built: announced with go-live countdown, early bird open, on sale, sold out, rumour (dashed border, no ticket button), festival lineup, sample (labelled). Tier ladder lights the open tier, strikes sold-out, dims upcoming.
- `/demo` shows the owner's radar read-only (artists panel included, alert history and settings left out). Scan now there is public, 1 per 2 minutes globally, and sends no alerts. Signed-in Scan now is 1 per 2 minutes per user and does send alerts.
- Scan now runs the news step for up to 40 of the user's artists (must-see first). The grounded web search stays in the first-run scan and the daily sweep job, because it is slower and costs more.
- `/api/health` folds per-user scan runs into one public `scan-now` entry so no user ids leak. System pulse dots: green OK, grey not run yet, amber running late (3x interval), red failing.
- "Not for me" on the dashboard and Telegram share one record (`alerts.user_action = dismissed`); dismissed shows leave the radar. Delete account removes the user and everything that cascades; the owner account can't be deleted from the UI.
- The radar timeline shows 12 cards at a time with "Show more", and the artists panel 12 with "Show all", so 100+ artists stay usable on a phone.
- Email is not switched on, so the Settings email toggle is disabled with an honest note, and no email alerts are queued.
- Show times like "18:30:00+05:30" are shown as "6:30 pm" everywhere.
- Phase 5, links: a ticket button or source link must open the exact page. Every URL is checked: it must load, land on a specific page (not a homepage, listing or bare social profile), and name the artist. Ticketing pages must also match this show's city or date, so a Delhi page is never used for a Mumbai show (status `mismatch`).
- Link statuses: `exact`, `ok` (loads and is specific, artist name not found in the text), `generic`, `broken`, `blocked` (bot wall we could not pass), `mismatch`, `unchecked`, `none`. People only see `exact`/`ok` ticket links; sources shown are `exact`/`ok`/`blocked` (blocked pages are specific URLs that work in a browser). Nothing unverified is ever shown or sent.
- Redirects: Google News links are decoded to the publisher's article, grounding links are followed, tracking parameters are stripped, and the final URL after redirects is what we store and show.
- BookMyShow and Bandsintown block plain requests (Cloudflare). Firecrawl gets through (tested), so a blocked ticketing page is verified with Firecrawl (1 credit), budget permitting, then Jina. The same scrape feeds tier extraction, so verification and tiers cost one credit together.
- Firecrawl budget: about 1,200 credits remain until the plan renews on 27 Oct. Daily cap 60: listings keep 10 in reserve for verification. The plan allows ~19 requests a minute, so scrapes are spaced 3.5 s apart and a 429 waits out Retry-After.
- No verified ticket page: the card says "Ticket page not confirmed yet" and the Telegram button is "Details & sources" (our event page, which lists every verified source) instead of a ticket button.
- Dispatch verifies any still-unchecked event before sending; links not verified within the time box are finished by the links job (every 10 min).
- Listings seeded and each verified with one scrape: District (music in Bengaluru), BookMyShow (music shows Bengaluru), AllEvents (Bangalore music), SortMyScene (home page). SkillBox's page returned almost nothing without a browser (1 KB), so it is not seeded. No platform offered a working all-India listing. Listings run every 6 h, and an unchanged page (hash of its event links) stops before extraction.
- Listing pages are split into ~9 KB chunks and only chunks naming a watched artist go to Gemini. An event's own page link, not the listing URL, becomes its source.
- Heartbeat: `GET /api/cron/heartbeat` via Vercel cron at 03:00 UTC (08:30 IST) messages the owner on Telegram: sources OK, new shows, alerts, Firecrawl credits, link verification counts and anything red.
- Job schedules are created with `scripts/setup-cron.ts` through the cron-job.org API (needs `CRONJOB_API_KEY`), or by hand from README.
- Card colours follow the ticket stage (`lib/stage.ts`), on the dashboard card (border and band), the Telegram poster (border and band) and the caption emoji: red (🔴) tickets live; purple (🟣) confirmed show with a ticket go-live date announced; orange (🟠) announced, unconfirmed, or tickets not live. Sold out is dark grey, rumours grey with a dashed border. "Confirmed" means confidence 0.9+ or two independent verified sources. Alert urgency (who gets pinged) is unchanged; only the look changed.
- Front end rebuilt in the "Stub" direction (owner's pick): ink black, ticket-paper accents, Big Shoulders poster type with Instrument Sans body. Stage colours unchanged.
- Cards flip between three faces: the show over a dimmed real concert photo, the artist's photo (Spotify image, or whatever was fetched; initials tile when none), and tiers/sources on paper. Tap to flip; the lead "On sale now" card and the landing example flip by themselves.
- Concert photos are static files in `/public/concert/` (`hero.jpg`, `crowd.jpg`, `lights.jpg`), dimmed with a CSS overlay (`--concert-dim`). A missing file shows the dark overlay only, so nothing breaks before the photos are added.
- Signed-in shell: Radar, My shows, Calendar, Profile (bottom tab bar on phones). Going and Saved are marks on a show (`alerts.user_action` = going / saved; "Bought it" in Telegram counts as Going). Profile holds "Add more artists", Spotify re-import, channels and cities (the old Settings page redirects there), alert history and Log out.
- Spotify connect plays an animation (FrontRow stub, streaming perforated line, Spotify mark) for about 1.7 s before the real OAuth redirect, and again while imported artists are read after the user returns.
- Concert photos (Pexels, free licence, no attribution required): hero.jpg = Pexels photo 21790480 (raised arms in a crowd), crowd.jpg = 952422 (crowd silhouette under stage lights), lights.jpg = 1190299 (blue-lit stage and crowd). Saved at 1600 px wide, 60 to 150 KB each. Unsplash blocks automated downloads, so it was not used.
- Palette moved to plum-black with a magenta highlight (`--magenta`), lilac-cream paper, and purple/magenta concert photos (Pexels 154147 hero, 36257830, 1763075). The purple "go-live date announced" stage colour is unchanged.
- Add to calendar: pressing it always adds the show to the in-app calendar (`calendar_entries`), shown in the calendar view under "In my calendar" with a tick on the day. If Google Calendar is connected it also creates the event there (all-day, or timed when the show has a time) with a deterministic event id, so pressing twice never duplicates; pressing again removes it from both. If not connected, the toast says so and offers Connect Google Calendar.
- Google Calendar connection is a second, optional consent for the single scope `calendar.events` (add events only), through the same Auth.js Google client, so no new redirect URI is needed. Sign-in itself still asks only for openid, email and profile. Tokens are kept on the existing `accounts` row and refreshed on use.
- Bookmark: the card's Save button is a bookmark icon (magenta when saved). Saved shows appear in My shows > Saved and in the calendar's "Saved" view; the calendar also has "All shows", "In my calendar" and "Going" views.
- Backgrounds: one fixed, dulled concert photo behind every screen (`components/shell/Backdrop.tsx`), crossfading to a different scene per area (landing/demo, onboarding and calendar, welcome and profile, radar and event pages, My shows). Five photos in one purple/magenta/dusk family (Pexels 154147, 1587927, 36257830, 11481894, 15509661), stored 2400 px wide and served by next/image at the right size and format for each screen (srcset, WebP/AVIF). A dark plum scrim and a slight desaturation keep text readable and the look plush. Stockcake blocks automated access (403) and Pexels' search is bot-protected, so the photos were chosen from Pexels pages via search and checked by eye.
- Logo and display type are slightly off-white (`--wordmark`), with "Row" in a dusty orchid (`--wordmark-soft`) taken from the photos; magenta is kept for small highlights only.
- Cards no longer carry a stock photo on their front. A card flips through four faces: the show (name, date, where) on plain plum, the artist's photo, a concert photo as it is (no text; one of two fixed photos, or the artist's own concert photo when we have one in `concertImage`), and tiers and sources on paper. We do not have per-artist concert photos yet, so every card uses the two stock photos for that face.
- Backup crawler: Scrape.do (key `CRAWLER_API_KEY`). Order for pages a plain request cannot read: Firecrawl while its daily budget lasts, then Scrape.do, then Jina. A plain Scrape.do request costs 1 credit and already returns the full BookMyShow event page (tested: verified exact, 9 KB of text); `render=true` (real browser, 5 credits) is used only when a listing comes back thin. Its HTML is converted to markdown with the links kept, so the extractors work unchanged. The free plan has 1,000 credits a month: budgets are 900 a month and 40 a day (`SCRAPEDO_MONTHLY_CAP`, `SCRAPEDO_DAILY_CAP`), spend is logged per call in `runs.scrapedo_credits`, and it shows in `/api/health` and the 8:30 heartbeat.
- Profile has two big tabs, Profile and Connections. Connections lists Telegram, Spotify, Google Calendar and Email, each with its logo and a green tick badge plus "Connected" when linked, and a summary ("2 of 4 connected"). The Profile page shows the same four logos with ticks as a link into Connections. Telegram: QR code and live "waiting for Start", test alert, pause/resume, unlink. Spotify: connect or re-import. Google Calendar: connect, reconnect, disconnect (revokes the grant at Google; shows already added stay). Email shows "not switched on yet" until credentials exist.
- First login: the first scan starts as soon as artists arrive (Spotify import, Spotify re-import, or a pasted list of 3+), in the background, once per user (`users.first_scan_at`); the welcome screen then shows the same results and does not repeat the web searches (artists swept in the last 12 hours are skipped). Linking Telegram queues and sends the user's alerts for everything already found (up to 8 at once, the dispatch job sends the rest), and tells them if nothing is announced yet. The scheduled jobs keep running independently. The scan has a time budget (50 s on the welcome screen, 34 s when it runs behind the Spotify import) so it always fits the 60 s function limit; whatever is unfinished stays queued for the next scheduled run.
- Crawler chain tested by breaking each provider in turn: Firecrawl, then Scrape.do, then Jina, then a plain fetch; each failure falls through to the next with no error shown to the user. Credits on 2026-10-12: Firecrawl 1,180 left until 27 Oct, Scrape.do 958 of 1,000, Jina free.
- Google sign-in now requests `calendar.events` together with identity at sign-up (granular consent: users can untick it). It stays in Testing mode with listed judges, because the scope is sensitive and unverified apps show Google's "hasn't verified this app" screen once.
- The daily heartbeat goes only to the owner's Telegram chat (the one user flagged `is_owner`, set only when the signed-in email equals `OWNER_EMAIL`); no other user can receive it.
- "On sale now" is always on the radar. It lists the viewer's own live shows first; when there are none, or in addition, it shows up to six real shows with tickets live for artists they do not follow yet, each with a "+ Follow" button (judges and new users never see an empty section). Those cards show a verified ticket link only.
- Every card on the radar, My shows and Calendar flips on its own while it is on screen, each on its own beat (hover or a tap takes over). Previously only the lead card did.
- SortMyScene removed as a source: its home page has no event listing (a marketing page, no event links even with a full browser render), so it only produced failures.
- Spotify top artists: the import read only the `medium_term` window (about six months), which is nearly empty for a light or new listener (the owner's account returned 9 there, 2 short-term, 50 long-term). It now merges long, medium and short term (up to 100 distinct artists; the owner's account gives 51), so top artists are no longer missed. The notice after an import now says how many followed and top artists came in, and says so when Spotify returned none.
- Playlists can't be a no-login substitute: Spotify's development mode refuses playlist tracks for the app (403 for playlist contents and user playlists), so importing needs the user connected, which needs them on the Spotify app's user list.
- A refused Spotify connection (usually 403: the account is not on the app's user list) is recorded and shows in the daily heartbeat with the email.
- Email without a domain: Gmail SMTP with an app password (already built; free; no domain; about 500 recipients a day). Everything email switches on by itself once `GMAIL_USER`, `GMAIL_APP_PASSWORD` and `EMAIL_FROM` exist: instant red alerts and amber fallback emails, the 09:00 IST digest (cron job added), unsubscribe links, the Connections tab tick, and an email copy of the daily heartbeat sent only to `OWNER_EMAIL`. Resend is not usable without a domain (it only sends to the account owner). Brevo or SMTP2GO would work with a verified single sender, but they are extra services; Gmail avoids that.
- Connect Spotify no longer waits on a timer before redirecting: the redirect starts on the next frame and the animation plays while the browser loads Spotify. If the page is restored with the Back button, the overlay is cleared. If the redirect stalls for 4 seconds, the overlay offers "Open Spotify" and "Cancel". (Report: the button seemed not to redirect. In tests, production and local both reached Spotify's login with the right redirect address, so the likely causes were the timer-based redirect, a restored page with the overlay stuck, or an in-app browser; all three are covered.)
- Onboarding is three steps now: Artists (adding and confirming on one page), Cities, Alerts. "Confirm artists and continue" goes straight to Cities with one tap, and the same button is also pinned at the top of the page (it stays visible while scrolling) with the artist count; it stays disabled while any "Which one?" choice is unresolved. The separate "Confirm your artists" step is gone; a saved old step 2 opens the combined page.
- Email via the Gmail API (no app password, no domain): the sender account is connected once with `scripts/connect-gmail-sender.ts` (Google sign-in on localhost, permission "send email" only), which stores `GMAIL_SENDER` and `GMAIL_REFRESH_TOKEN` in `.env.local` and Vercel. When both exist, all email goes through it (alerts, digest, heartbeat copy), `emailConfigured()` turns true everywhere, and SMTP/Resend settings are ignored. While the Google app is in Testing mode, Google expires this refresh token after 7 days: the script has to be re-run weekly until the app is published. A failed send names the cause in the run log and heartbeat.
