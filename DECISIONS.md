# Decisions

- App named FrontRow (brief title was ShowRadar); tagline "Be the first to know about a show."
- Project lives in `Mesa Ai/frontrow`, its own git repo, separate from the other projects in that folder.
- Next.js 16.4: `middleware.ts` is now `proxy.ts` (Node runtime). Proxy does only an optimistic session-cookie check; every page and API route re-checks the session server-side.
- Next 16 scaffold enables `cacheComponents`, so route segment config like `export const dynamic` is not allowed; route handlers are dynamic by default.
- Drizzle uses the `neon-http` driver via `@neondatabase/serverless`: one lightweight client per call, no pool to leak.
- `pg_trgm` is enabled at the top of the first migration (`drizzle/0000_init.sql`).
- Auth.js v5 with database sessions; only `openid email profile` scopes. Owner flag is set on sign-in when the email equals `OWNER_EMAIL`.
- Dark mode by default; light via `data-theme="light"`. All colours/radii live in CSS variables in `app/globals.css`.
- `/api/health` is public and reports only real values; per-job runs and Firecrawl credits are empty until those jobs exist.
- Secrets live in `.env.local` (gitignored) and in Vercel env vars; `.env.example` lists names only.
- shadcn/ui is deferred until the first component that needs it (Phase 1+), to keep Phase 0 minimal.
- Production URL: https://frontrow-pi-three.vercel.app (Vercel alias, stable). Deployed from CLI for now; GitHub link to be added so pushes to main deploy.
- Google consent screen stays in Testing mode by the owner's choice (deliberate change from the brief): judges' emails are added as test users in Google Cloud Console (max 100). Unlisted emails see Google's own "access blocked" page; /demo stays public. Switching to Publish later needs no code change.
- Phase 1: verified live APIs first. Gemini key works (sent as `x-goog-api-key`); newest stable Flash is `gemini-3.8-flash` (set as `GEMINI_MODEL`). Spotify search returns 10 results with photos and genres. MusicBrainz works with the User-Agent.
- Spotify search and artist lookup use the app's client-credentials token, not the owner's refresh token, so identity resolution keeps working even if the owner's personal connection breaks. The per-user connection (owner and allowlisted users) is used only for the followed/top import. Deviation from the brief's "owner token for search", for robustness.
- Spotify's redirect URI must use `127.0.0.1`, not `localhost`, so the Spotify connect flow is tested on the production URL (the Google sign-in cookie is on `localhost` locally).
- Resolution rules: auto-accept only when exactly one result matches the normalized name exactly; two exact matches (e.g. duplicate Spotify profiles for the same name) go to the "Which one?" tray. Nothing at all in Spotify or MusicBrainz becomes `unverified` ("Name only").
- `needs_review` is represented by open `artist_candidates` rows, not artist rows, so nothing unconfirmed is watched or matched.
- Alias enrichment (MusicBrainz aliases, origin, mbid) is best effort in `after()` with a 40s budget, because MusicBrainz answered at 2-3s per call. Artists beyond the budget keep derived aliases (leading "The", "&"/"and") and are enriched on a later pass.
- A MusicBrainz match by name alone is accepted only if it is a single perfect-score exact-name hit; otherwise the mbid comes from the Spotify URL relation or is left empty.
- First sign-in with `onboarding_step = 0` is redirected from `/radar` to `/onboarding`. Onboarding steps 1 and 2 are built; cities and alerts steps come in later phases.
- Phase 2: Gemini grounding and structured output are kept in separate calls (the combined call returned no text). Grounded sweep answers become raw items with `SOURCE_URL:` lines; grounding links are Google redirects, so each is followed once (4s budget) to the real page URL.
- Sweep "nothing announced" is decided by a structured field (`has_upcoming_india_show`), not by the word NONE, because the model wraps its answer in headings. Those sweeps store no raw item and spend no extraction call, but still update `last_checked_at` and "Last in India".
- News is pre-filtered before Gemini: a headline must name a watched artist (normalized, whole-word) to become a raw item. Generic feeds use the same gate. This keeps Gemini calls to real candidates only.
- Matching uses a JS port of pg_trgm similarity over the watched list (same measure, no per-name round trips); thresholds as in the brief (0.85, 0.92 for name-only, Gemini yes/no for 0.7-0.85).
- A sweep is about one named artist, so if Gemini spells that artist differently, the sweep's artist hint is trusted for non-festival events.
- Decide queues `alerts` rows (status `pending`, or `digest_pending` for info) but sends nothing: dispatch is Phase 3. Re-deciding is idempotent through the unique constraint; an unsent alert is upgraded if urgency rises.
- First-run scan: artists swept in the last 12 hours are not swept again (shared cache across users); up to 8 are swept, must-see first, and the rest are reported as "Deep check runs tonight".
- First-run finishes onboarding (`onboarded_at`, step 4) for now; the Cities and Alerts steps are inserted before it in Phase 3. `/welcome` is reached from "Find my shows" on the confirm step.
- Owner radar seeding (`scripts/seed-owner-radar.ts`): a grounded Gemini query finds artists with announced India shows, they are resolved through Spotify and set to must-see on the owner's list, then swept and processed. Everything stored carries real source URLs.
- Phase 3: Telegram bot is @FrontRowShowBot (username saved in env). Webhook registered with `scripts/set-webhook.ts`; every call checks `X-Telegram-Bot-Api-Secret-Token`, and the route always answers 200 so a bad update is never retried forever.
- Email templates are plain HTML strings, not React Email: one fewer dependency, same output. Unsubscribe links are HMAC-signed (AUTH_SECRET) and also work as one-click POST.
- Dispatch claims rows atomically (`for update skip locked`), so overlapping runs never double-send. At most 5 instant alerts per user and channel per run; the rest roll into the next digest (a first sync must not flood anyone).
- Telegram "blocked the bot" unlinks the chat and re-queues that alert by email. A failed poster image falls back to a text message with the same buttons.
- Alerts for events dated in the past are skipped, never sent. Email alerts stay `pending` (and are shown as waiting) until email credentials exist.
- The digest records one `digest` alert row per (user, event), so no event is in two digests; info alerts are included whatever their age.
- Test alert uses the nearest real event (home city first), labelled Test. Only with none, a stored `is_sample` event is used, labelled Sample.
- Onboarding steps 3 (cities) and 4 (alerts) are built; "Find my shows" on step 4 goes to /welcome. Existing onboarded users reopening /onboarding land on step 2.
